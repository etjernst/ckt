CKT pipeline parallelization: how it works and where it duplicates

Snapshot 2026-05-12, branch worktree-grc-pipeline-refactor. Aim: explain what we're doing now, then call out duplication concerns we should think about before merging.

The big picture

The pipeline is not parallel inside any single Stata process. What we do is run multiple Stata processes concurrently at the OS level, and let the filesystem mediate so they don't fight over the same fits. Three pieces make this work:

  1. A resume-if-exists guard baked into run_grc and run_grc_robust_vv. If a cell's terminal ster (_g$vsfx.ster) is already on disk and the global ${skip_if_exists} is 1, the program prints SKIP <estname> and returns immediately.
  2. A master entry point (0_master.do) that walks the whole pipeline sequentially, plus a thin wrapper (run_master_resume.do) that just sets ${skip_if_exists}=1 before calling it. Same script, different mode.
  3. Three family slice drivers that run only a subset of 9_GRC_extras.do's cells (one extra-regressor family each), with ${skip_if_exists}=1 always on:
    • run_extras_maxexpsh.do --- 9 stems = 36 fits = 180 sters
    • run_extras_birth.do --- 4 IDN stems = 16 fits = 80 sters
    • run_extras_cnu.do --- 4 IDN cnu stems = 16 fits = 80 sters

Yesterday's overnight run was three concurrent stata-mp -e do run_extras_*.do processes plus the master pipeline in resume mode, all in the same RP7/output/ directory, coordinating only through the presence or absence of _g.ster files.

How the resume guard works

The guard lives in 0_programs.do around line 1847 (run_grc) and 2753 (run_grc_robust_vv):

if "${skip_if_exists}" == "1" {
    capture confirm file "$output/`estname'_g${vsfx}.ster"
    if _rc == 0 {
        di as text "run_grc: SKIP `estname' (`estname'_g${vsfx}.ster present)"
        exit
    }
}

Two design choices to flag here:

  • The check is on the last ster a cell writes (_g, the group-average), not the first. So a cell crashed mid-fit (e.g. _n written but not _g) is correctly re-attempted.
  • The check happens inside run_grc, not at the caller. Every caller --- 4_GrRC, 5_GrRC_NonAg, 7_GrRC_hukou, run_grc_with_extra_regressor --- gets the resume behaviour for free. This is the right factoring; no per-caller boilerplate.

Why the slice drivers can race the master safely

If 0_master.do (in resume mode) and run_extras_birth.do both reach the same un-fit cell at roughly the same instant, both processes pass the capture confirm file guard (the ster doesn't exist yet), both run the GMM fit, and both call estimates save. The second save wins; the resulting ster is byte-identical (deterministic optimizer, same data, same initial values) so nothing observable changes. The cost is one redundant fit, not a corrupted ster.

In practice the slice drivers each touch a distinct family of cells (maxexpsh, birth, cnu × experience), and 9_GRC_extras.do walks them in family order, so race windows are short and overlapping work is rare. The header comment in run_extras_maxexpsh.do notes this explicitly.

Where the duplication lives

This is the part to look at hard. Each slice driver is ~96 lines, but only 4 to 11 lines inside capture noisily { ... } actually differ between them. The rest is shared scaffolding repeated three times.

The repeated blocks

  1. The $dir resolution block (~14 lines per file, ~42 lines total). Identical username-to-path lookup in every slice driver. The header comment in each one literally says "Mirrors 0_master.do; keep these blocks in sync if 0_master.do gains new users." That's a smell --- it's documenting a maintenance burden rather than removing it. This is also duplicated in 0_master.do itself, so the same block exists in four places.
  2. The values switch (global values "nominal" + ~7-line comment block). Identical in all three drivers.
  3. The bootstrap includes: include "$dir/scripts/0_path_config.do" + quietly include "$scripts/0_programs.do". Identical in all three.
  4. Global flags: global skip_if_exists 1 + global copyOverleaf 0. Identical.
  5. Log + error wrapper: capture log close / log using "$logs/<name>.log", replace / capture noisily { ... } / local saved_rc = _rc / log close / error print / exit, STATA clear. Same in all three; only the log filename and body differ.
Concrete failure mode this invites. The CLAUDE.md says $dir for user maand varies by worktree, and the current value in 0_master.do is C:/git/ckt/.claude/worktrees/grc-pipeline-refactor/RP7. If we add a new worktree, we have to update four files to keep them in sync (master + three slice drivers). Easy to miss one. And we already commented out 4 alternate worktree paths in 0_master.do but not in any of the slice drivers.

What actually has to live in each driver

Strip the boilerplate and a slice driver only needs to declare:

  1. Its name (for the log file)
  2. Its cells (the body of capture noisily { ... })
  3. Optionally, the values switch (nominal vs real)

Everything else --- $dir resolution, path config, programs include, skip flag, log open/close, error handling --- is identical across drivers.

A cleaner structure

Two changes would collapse the duplication without changing behavior:

Change 1: extract $dir resolution into its own include

Create 0_dir_resolution.do with the user-block, then have 0_master.do and every slice driver call it as the literal first include. The user-block lives in one place; adding a new worktree is a one-file edit.

* 0_dir_resolution.do  --- single source of truth for $dir per user
if "`c(username)'"=="maand" {
    global dir = "C:/git/ckt/.claude/worktrees/grc-pipeline-refactor/RP7"
    global overleaf = "C:/Users/maand/Monash Uni Enterprise Dropbox/..."
}
if "`c(username)'"=="kleemans" { ... }
* etc.

if "${dir}" == "" {
    di as error "0_dir_resolution: \$dir not set for user `c(username)'."
    exit 198
}

Change 2: extract the bootstrap envelope into its own include

Create 0_slice_bootstrap.do for the path config + programs load + skip/copy flag setup. With both extracts, a slice driver becomes about 25 lines instead of 96, and the only repeated lines are the include calls themselves:

* run_extras_birth.do  --- after refactor
clear all
version 17

if "$values" == "" global values "nominal"

include "0_dir_resolution.do"
include "$dir/scripts/0_path_config.do"
quietly include "$dir/scripts/0_programs.do"
include "$dir/scripts/0_slice_bootstrap.do"   // sets skip_if_exists=1, copyOverleaf=0

capture log close
log using "$logs/run_extras_birth$vsfx.log", replace
capture noisily {
    run_grc_with_extra_regressor, country(IDN) spec3(cuu) regressor(urbanbirth)
    run_grc_with_extra_regressor, country(IDN) spec3(cub) regressor(urbanbirth)
    run_grc_with_extra_regressor, country(IDN) spec3(iuu) regressor(urbanbirth)
    run_grc_with_extra_regressor, country(IDN) spec3(cnu) regressor(urbanbirth) ///
        data_path_override("$dirdata/processed/IDN_unb.dta")
}
local saved_rc = _rc
log close
if `saved_rc' != 0 di as error ">>> run_extras_birth FAILED with rc=`saved_rc'"

Could go further and factor the capture log close ... log close ... if rc != 0 envelope into a one-shot helper too, but that's diminishing returns for three files.

What this would not change

  • The actual parallelization model --- still OS-level concurrent Stata processes mediated by skip_if_exists.
  • The slice families and their cells.
  • Anything inside run_grc or run_grc_with_extra_regressor.
  • The master entry point's behavior in either mode (full or resume).

This is pure refactor: move the boilerplate out of the slice drivers into a shared include. No estimation results would change.

Open questions

  1. Do we want to refactor before merging the branch, or land the slice drivers as-is and clean up later? Argument for before: the duplication is small, and merging now bakes it into main. Argument for after: the refactor is a separate PR-sized change and we already have a lot of moving parts on this branch.
  2. Is 0_dir_resolution.do worth extracting on its own, or should we just have a single 0_slice_bootstrap.do that does the whole envelope? My read: the $dir block is the highest-pain duplication (four places, varies per worktree, easy to forget). Worth extracting even if we leave the rest of the envelope inline.
  3. Anything else duplicated that I missed? The smoke drivers (_smoke_full.do, _smoke_extras_dispatch.do, etc.) likely have the same boilerplate too --- worth checking.
