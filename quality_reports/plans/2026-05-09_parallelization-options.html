Parallelizing the GRC extras pipeline

Three options for compressing the remaining serial work in 9_GRC_extras.do. Drafted 2026-05-09. Planning only --- no implementation.

The core lever. Stata MP cannot parallelize the gmm / nlcom bottleneck within a single process, so multi-core is irrelevant here. Multiple Stata instances on the same machine, each handling a disjoint slice of the work, is the only practical speedup. The codebase already supports this through ${skip_if_exists} --- any instance that finds a target ster on disk skips that cell in seconds.

3. Three plans, side by side

Each new instance gets a slice driver (set global skip_if_exists 1, set its own log filename, source 0_path_config.do + 0_programs.do, run a target block) and gets launched detached via PowerShell. The slice is chosen so PID 4864 won't reach it for many hours, removing the race window.

Plan A --- minimal: 2 new instances

Speedup: 32 h → 13 h (~2.5x). Two new drivers, two log files, two detached Start-Process calls. Lowest setup cost.

Plan B --- balanced: 3 new instances

Same 13 h critical path as Plan A. The added instance D doesn't move the floor because instance C (birth) is already longer. The benefit of adding D: PID 4864 finishes its work after ~3.5 h instead of 11 h, freeing the machine of one running process for the rest of the night. Marginal but cheap.

Plan C --- aggressive: split the long blocks by stem (5--6 instances)

The IDN birth dispatcher is the critical path. To reduce it, split birth into stem-level instances; spec3=cuu is the only ~3.5 h stem within birth, the rest are short.

Speedup: 32 h → 8 h (~4x). The new bottleneck is the IDN cnu sub-block, which we left whole. To go faster still, split cnu by family (4 instances at ~2 h each); the new floor would be ~3.5 h, set by the slowest single IDN-cuu stem. That asks for 9--10 concurrent Stata instances and runs into diminishing returns: setup, log management, and concurrent-write watchfulness compound.

5. Risks and mitigations

RiskLikelihoodMitigation
Two instances fitting the same cell concurrently → race on the binary .ster file. Low Partition slices so PID 4864 reaches them last. Stata's estimates save writes atomically (temp + rename); both writes succeed, late one wins; estimation is deterministic so contents identical.
Two instances opening the same log file ($logs/9_GRC_extras.log). High if not handled Each driver sets its own per-instance log path before sourcing the slice block.
Stata MP license refusing concurrent instances. Low (personal MP allows multiple) Confirm by launching a second instance briefly (no harm).
Memory pressure: 4 instances × ~250 MB ≈ 1 GB. Negligible Modern machine.
Concurrent reads of the data file. Negligible Read-only access; Windows handles fine.
Mid-fit collision: PID 4864 reads a half-written ster from instance C. Very low (atomic writes) Even if it occurred, estimates use would error and the cell would be re-fitted in the next iteration; not silent corruption.
Drift from the corrected 0_programs.do. None All instances source the same file; new sters from new instances are born correct (no sidecar override needed for them).

6. Open questions before implementation

  • Is 9_GRC_extras.do structured so each family is a contiguous block we can include or sub-source selectively, or does it fall through such that we'd need a real refactor to slice cleanly?
  • Is the log path opened directly as $logs/9_GRC_extras.log, or is there a global we can override per-instance?
  • Are there any cross-family dependencies (e.g., a regressor created in one family's data_setup that another family relies on) that would force a particular ordering within a single instance?
  • For instance C (birth), what's the actual spec3 set --- is it really cuu/cub/iuu like the others, or does the dispatcher add extra spec3s? This determines the per-stem split.

Three short reads of 9_GRC_extras.do would settle all four. Worth doing before sizing up beyond Plan B.

If you want maximum speedup with minimum setup

Plan A. Two new drivers, two new log files, two Start-Process calls. Cuts ETA from ~32 h to ~13 h.

If you want PID 4864 to wind up tonight too

Plan B. Adds maxexpsh as a third slice. Same 13 h critical path but PID 4864 finishes in 3.5 h and frees the box.

If 13 h is too long

Plan C. Split birth by stem (3 instances, longest 3.5 h). New floor: 8 h, set by IDN cnu. Splitting cnu pushes the floor to ~3.5 h at the cost of orchestrating ~10 instances.

What you cannot beat

The slowest single IDN-cuu stem runs ~3.5 h on one core. That's the irreducible floor unless we change the estimator or the nlcom structure.
